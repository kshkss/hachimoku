# ADR-102: ブラウザ拡張機能を用いた分散型（ゼロインフラ）スクレイピング

## ステータス
Accepted

## コンテキスト（背景）
家計簿アプリに求められる最大の機能価値の1つが「銀行やクレジットカードからの明細自動同期」です。
しかし、この「アグリゲーション（スクレイピング）」をサーバーサイドで行うアプローチは、近年以下の大きな壁に直面しています：
1. **銀行のスクレイピング規制**: 多くの金融機関が自動スクレイピングを遮断、または代理取得を明確に規約で禁止している。
2. **多要素認証（MFA）の突破難度**: ワンタイムパスワードや画像認証、パズル認証が導入され、サーバーのバックグラウンドワーカーによる完全自動取得はほぼ不可能。
3. **莫大なサーバー・プロキシコスト**: 金融機関からIPブロックを避けるためのプロキシ費用、ブラウザをシミュレートするヘッドレスブラウザ（Puppeteer等）のサーバーCPU/メモリリソース、保守にかかるエンジニアリングコストが急騰する。

## 意思決定
金融機関データのスクレイピング処理をサーバーサイドから完全に排除し、**ユーザー自身のWebブラウザ上で動作する「ブラウザ拡張機能（Extension）」に100%委譲する「分散型スクレイピングワーカー」モデル**を採用します。

### 1. 動作のメカニズム
* ユーザーのブラウザ（PCやAndroid等）に「hachimokuアグリゲーション拡張機能」をインストールしてもらいます。
* データの自動更新指示をトリガーに、拡張機能がバックグラウンド、または非表示の iframe 内で銀行サイトを開きます。
* ユーザー自身が普段そのブラウザでログインしている「有効なセッション（Cookie）」をそのまま再利用して自動アクセスするため、銀行側からは「正規のユーザーが自分のブラウザでアクセスしている」ようにしか見えず、不審なアクセスとしての検知や遮断を完全に回避できます。

### 2. 「おもてなしUX」割り込み処理
* パズル認証や、メール・SMSでのワンタイムパスワード（MFA）が必要な場合、拡張機能は処理を一時停止し、hachimokuアプリ側に「入力が必要です」というプッシュ/インラインUIをポップアップさせます。
* ユーザーがその場でMFAコードを入力すると、拡張機能に値が引き渡され、スクレイピングを続行します（手動と自動の安全な融合）。

### 3. プラグイン型マイクロ拡張機能構造
* 銀行ごとに個別パッケージ（スクリプト）としてプラグイン化。ある金融機関のUIが変更されても、そのプラグインだけを素早くアップデートする疎結合設計とします。

## 影響・トレードオフ
* **メリット**:
  * **インフラコストゼロ**: 何万人のユーザーが毎日一斉にデータ取得しても、CPUパワーを消費するのはユーザーの手元のブラウザであるため、運営側のサーバー代・プロキシ代は恒久的に **0円** です。
  * **セキュリティ安全性の向上**: ユーザーの銀行のログインIDやパスワードをサーバーに送信・保管する必要が一切ありません。クレデンシャルはユーザーの手元から一歩も外に出ません。
* **デメリット**:
  * ユーザーに「ブラウザ拡張機能」を追加でインストールしてもらうという最初期の手間（摩擦）が生じます（特にiOS Safariなどの制約が厳しい環境では、手動CSVインポート等の代替手段が必要）。
