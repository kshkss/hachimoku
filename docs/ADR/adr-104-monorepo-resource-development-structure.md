# ADR-104: モノレポ（Mono-Repository）構成による開発リソースの最適化

## ステータス
Accepted

## コンテキスト（背景）
個人開発や少人数の小規模チームで、クライアントアプリ（`/app`、場合によってはブラウザ拡張機能）と同期サーバー（`/sync`）を並行して構築する場合、リポジトリが分散していると以下のような問題が頻発します：
1. **プロトコルの乖離**: クライアントとサーバーのAPI定義や暗号化データ構造のズレが検知しづらく、デプロイ時に互換性バグが発生する。
2. **開発環境構築の複雑化**: 各コンポーネントを別々にチェックアウトしてビルドする必要があり、ローカルでの一気通貫した動作検証やデバッグが億劫になる。
3. **リソースの断片化**: ドキュメント、ADR、インフラコードがばらばらに管理され、プロジェクト全体のアーキテクチャの現状把握が困難になる。

## 意思決定
プロダクトの全ソースコード、ドキュメント、インフラ定義を単一のコードベース **「モノレポ（Mono-Repository）」** で管理します。

### 1. 構造設計
* **/app**: クライアントアプリケーション（Rust / 画面表示・ドメイン・ローカルDB）。
* **/sync**: 同期バックエンド（Go / APIサーバー）。
* **/extension**: ブラウザ拡張機能（JavaScript / スクレイピング）。
* **/protocol (または /shared)**: クライアントとサーバー、拡張機能間でやり取りするJSONメッセージ、API定義、共通定数。
* **/docs (または /adr)**: 本ADRをはじめとするアーキテクチャ設計・要件ドキュメント。

### 2. 開発項目とロードマップの集約
開発項目は、個別の言語やリポジトリの境界を超えて「1つのユーザー体験」としてチケット管理します。
プロトコル（スキーマ）定義に変更が入った場合、モノレポ内の1つのプルリクエストで `/app`、`/sync`、`/protocol` のコードを同時に修正・テストし、矛盾がない状態（Atomic Commit）でマージします。

## 影響・トレードオフ
* **メリット**:
  * 依存関係の可視化：クライアントからサーバー、スクレイピング拡張機能まで、ローカルで一発で起動できるスクリプト（`Makefile`等）を用意でき、開発効率（DX）が飛躍的に向上します。
  * ドキュメントとコードの乖離防止：本ADRのような仕様書がコードと同じコミットで管理されるため、設計の陳腐化を防ぎやすくなります。
* **デメリット**:
  * リポジトリのファイルサイズ・コミットログが肥大化します。
  * 異なる言語（Rust, Go, JS）が混在するため、CI/CDパイプライン（GitHub Actionsなど）のキャッシュ制御や条件付き実行（変更があったディレクトリだけテストを走らせる）の初期構築コストがやや高くなります。
