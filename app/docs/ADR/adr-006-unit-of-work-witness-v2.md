# ADR-006-v2: Witnessパターンによる型安全なトランザクション境界制御

## ステータス
**決定** (ADR-006-v1 より更新。ローカルクライアント /app のメモリ安全性・スレッド安全性・ACID制御にフォーカス)

## コンテキスト（背景）
家計簿アプリ `hachimoku` のローカルDB（SQLite等）へのデータ保存において、アプリケーション層はデータの整合性を守るための「トランザクション（Unit of Work）」を厳格に制御する必要があります。
例えば、1つの仕訳を更新する際、関連する残高キャッシュの更新や、未分類タグの変更などを1つのアトミックなトランザクションとして実行しなければ、途中でアプリが強制終了した場合などにデータ破損が発生します。

従来のレイヤードアーキテクチャでは、リポジトリが `save(&self, book: Book)` のようなメソッドを提供しますが、これには以下の深刻なバグのリスクがあります：
1. 開発者がトランザクションの開始（Begin）を忘れ、自動コミットモードで個別の保存メソッドをバラバラに呼び出してしまう（データ不整合の発生）。
2. トランザクションをまたいで保存ロジックが走り、コネクションロックのデッドロックや、古いデータの書き戻し（ロストアップデート）が発生する。

ドメイン層に「トランザクション」や「データベース接続」といったインフラの具体的な知識を持ち込まずに、アプリケーション層から「トランザクションを経由した保存」を強制するための静的な仕組みが求められていました。

## 意思決定
`/app` のアプリケーション層とインフラ層の境界において、**Unit of Workパターン**と、Rustの型システムを活用した**Witness（目撃者/Capability）パターン**を採用します。

```
     [ Application Layer (Usecase) ]
                   │
                   │ 1. tx = uow_manager.begin()  ── トランザクションの開始
                   ▼
     [ UpdateTransaction (UowTokenを所有) ]
                   │
                   │ 2. token = tx.token()        ── 証拠(Witness)トークンを取得
                   │ 3. repo.save(token, &book)   ── トークンを引数として強制要求
                   ▼
     [ Repository (Infrastructure) ]
                   │
                   │ 4. トランザクション内でSQLiteへ書き込み (型レベルで安全を保証)
                   ▼
     [ Application Layer ]
                   │
                   │ 5. tx.commit()               ── コミット
```

### 1. Witness（証明・権限）トークンの導入
ドメイン層・アプリケーション共通層に、空のマーカートレイトである **`UowToken`** （または `RevisionToken`）を定義します。

```rust
// ドメイン/アプリケーション境界に定義される、具象実装を持たない証拠トレイト
pub trait UowToken {}
```

リポジトリの書き込みメソッド（Writer Trait）は、この `UowToken` を参照として引数に受け取ることを**コンパイルレベルで強制**します。

```rust
pub trait BookRepository {
    // 保存には必ず、有効なトランザクションの証拠（token）が必要
    fn save(&self, token: &dyn UowToken, book: &Book) -> Result<()>;
}
```

### 2. UpdateTransaction (Unit of Work) によるトークン発行
トランザクションを管理する `UpdateTransaction` 構造体（アプリケーション層/インフラ層の境界）のみが、この `UowToken` を実装した実体（非公開なインナートークン）を生成・保持できます。

Usecaseはトランザクションを開始して `UpdateTransaction` を取得し、そこから `UowToken` を引き出してリポジトリに渡します。これ以外の経路で `UowToken` を偽造することはRustのモジュールカプセル化（`pub(crate)` 等）により不可能です。
これにより、**「トランザクションを経由しなければ、リポジトリの保存処理を呼び出すコード自体がコンパイルを通らない」**という強力なコンパイルタイム安全性が確保されます。

### 3. 遅延トランザクション（Late-acquired transaction）によるプール保護
ローカルSQLiteのコネクションロックを不必要に占有しないため、ユースケース内でバリデーションや外部暗号化処理、事前計算を行っている間はトランザクションを開始しません。
実際にDBへの物理的な書き込みが発生する直前の、最小限のクリティカルセクションにおいてのみトランザクションを開始する「遅延トランザクション」方針を徹底します。

## 影響
* **メリット**:
  * 「トランザクションの掛け忘れ」や「自動コミットでの保存」によるデータ不整合が、コンパイル時に100%防止される。
  * リポジトリの実装を変更（SQLiteからIndexedDB、メモリ内モック等へ移行）しても、型によるトランザクションの安全性保証の仕組みはそのまま維持される。
* **デメリット**:
  * すべての保存メソッドの引数に `token` を引き回す必要があり、コードの記述量がわずかに増加する。
