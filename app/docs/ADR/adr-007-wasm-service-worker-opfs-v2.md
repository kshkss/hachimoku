# ADR-007-v2: WASM ＋ Service Worker ＋ OPFS SQLite によるブラウザ内ローカル永続化

## ステータス
**決定** (ADR-007-v1 より更新。クライアントアプリ /app のブラウザ完結動作・PoC検証アーキテクチャにフォーカス)

## コンテキスト（背景）
家計簿アプリ `hachimoku` のコア価値である「ローカルファースト」をデスクトップPCやモバイルで手軽に体験してもらうため、デスクトップアプリ（Tauri等）のインストールをユーザーに要求せず、**一般的なWebブラウザ（Chrome, Safari, Edge等）にアクセスするだけで完全なローカルファーストとして自律動作する仕組み**を模索していました。

しかし、ブラウザ環境でのローカル永続化には以下の高い技術的ハードルがあります：
1. **Local Storage/IndexedDBの制限**: リレーショナルな家計簿データ（数万件の仕訳、集計インデックス、多通貨ポジション勘定）を非SQLのKey-Valueストア（IndexedDB）で扱うのは、スキーマ管理やクエリ速度の面で非常に困難。
2. **SQLiteの同期I/Oとブラウザの非同期の壁**: 標準のSQLite（C言語版）はファイルシステムに対して同期的（Synchronous）なディスク書き込みを要求しますが、WebブラウザのJavaScript File APIはすべて非同期（Asynchronous）であるため、そのままではブラウザ内でSQLiteを正常かつ高速に動作させることができません。
3. **サーバー不要論**: HTMXによる動的更新を維持しながら、バックエンドサーバーを完全に排除し、ブラウザ内部だけでリクエストを処理して完結させる必要があります。

## 意思決定
ブラウザ完結型の `/app` 動作モデル（PoCおよび検証フェーズ）として、**「Service Workerによるリクエストインターセプト」**、**「Go/Rust WebAssembly（WASM）による内部バックエンド」**、および**「OPFS（Origin Private File System）上の本物SQLite永続化」**を組み合わせた画期的なアーキテクチャを採用します。

```
                    【 Webブラウザ内部 (Sandbox) 】
  ┌────────────────────────────────────────────────────────┐
  │ [ HTMX / Alpine.js (Frontend UI) ]                      │
  │           │                                            │
  │           │ 1. fetch("/api/v1/journals")               │
  │           ▼                                            │
  │ [ Service Worker (JS) ] ── HTTPリクエストを空中で奪取      │
  │           │                                            │
  │           │ 2. WASMのエントリポイント関数を直接キック     │
  │           ▼                                            │
  │ [ Go/Rust WASM (Domain/Usecase/ORM) ]                  │
  │           │                                            │
  │           │ 3. 同期的なSQLiteドライバ経由でI/O発行         │
  │           ▼                                            │
  │ [ FileSystemSyncAccessHandle (OPFS) ] ── 同期アクセス   │
  │           │                                            │
  │           ▼                                            │
  │ [ SQLite Database (hachimoku.sqlite) ] ── 物理的なファイル│
  └────────────────────────────────────────────────────────┘
```

### 1. Service Worker による「Backend in the Frontend」の構築
フロントエンド（HTMX）から送信される通常の `/api/...` に対するHTTP `fetch` リクエストを、ブラウザのバックグラウンドで常駐する **Service Worker** が横取り（ハイジャック）します。
Service Workerはリクエストをインターネットに送信せず、メモリ上にロードされている WASM アプリケーションのルーティングハンドラへ直接引き渡します。これにより、クライアントUI側からは、あたかも本物のリモートサーバーと通信しているかのように、ローカルのWASMバックエンドをシームレスに操作できます。

### 2. OPFS (Origin Private File System) と同期書き込みハンドルの活用
SQLiteが要求する「同期的なファイルシステム書き込み」をブラウザ内で実現するため、HTML5の最新仕様である **OPFS（Origin Private File System）** を採用します。
* OPFSは、ブラウザがオリジン（ドメイン）ごとに提供するプライベートで高速なストレージ領域です。
* Web Worker（Service Worker含む）のスレッド内でのみ、**`FileSystemSyncAccessHandle`** という同期I/Oを提供する特別なハンドルを取得できます。これを利用して、SQLiteエンジンが直接ブロック書き込みを行えるようにマウントします。

### 3. CGOフリーなWASM対応SQLiteドライバの選定
Go/Rust WASMからこのOPFS SQLiteを安全に操縦するため、WASM環境をネイティブサポートし、かつCGO依存を完全に排除した **`ncruces/go-sqlite3`** （Go環境）またはRustのwasmターゲット対応SQLドライバを採用します。これにより、ブラウザのタブを閉じたりリロードしたりしても、ローカルデータベースファイルが完全に維持される「消えないブラウザ内SQLite」が実現します。

## 影響
* **メリット**:
  * ユーザーは「ブラウザで特定のURLを開く」だけで、完全にローカル動作する極めてセキュアな家計簿（データはサーバーに1バイトも送信されない）を即座に利用できる。
  * デスクトップアプリ（Electron/Tauri等）をビルドして配布する手間とコストが大幅に削減される。
  * HTMXによるテンプレート部分差し替えのコードが、WASM内部からそのままHTML文字列として出力され、驚異的な応答速度（レイテンシほぼゼロ）を達成する。
* **デメリット**:
  * OPFSの同期アクセスハンドル（`FileSystemSyncAccessHandle`）は一部の古いブラウザや、特定のセキュリティコンテキスト（HTTPS必須）でしか動作しないため、実行環境の前提条件が厳格になる。
  * WASMバイナリのサイズ（数MB〜十数MB）が大きくなり、初回ページロード時のダウンロード時間が長くなる。これを解消するため、Echo等の不要なフル機能フレームワークの依存を排除し、WASMのコードサイズ削減に努める必要がある。
