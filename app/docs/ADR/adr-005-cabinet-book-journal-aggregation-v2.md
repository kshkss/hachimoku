# ADR-005-v2: Cabinet集約のType State管理とBook/Journal集約の完全分離

## ステータス
**決定** (ADR-005-v1 より更新。ローカルクライアント /app のドメイン設計およびメモリ制御にフォーカス)

## コンテキスト（背景）
`hachimoku` のドメインモデリングにおいて、データの所有権とライフサイクルを適切に表現する必要があります。
特に「Cabinet（キャビネット：最も大きなデータの入れ物）」の中に「Book（帳簿）」があり、その中に膨大な「Journal（仕訳）」が存在するという階層構造を持ちます。

このドメインモデルを設計するにあたり、以下の2つの深刻な課題に直面しました：
1. **共有権限の複雑さ**: 自分が所有している原本キャビネットと、他者から共有された参照キャビネットでは、行える操作（帳簿の追加、仕訳の編集、連携設定など）が本質的に異なります。これを実行時に `if cabinet.is_shared() { ... }` のようにチェックすると、判定漏れや権限チェックのバグが発生しやすくなります。
2. **オンメモリのパフォーマンス問題**: 1つのBook（帳簿）に数千から数万件の仕訳（Journal）が紐づきます。DDD（ドメイン駆動設計）の原則に従って Book を1つの「集約（Aggregate）」とし、内部に仕訳のベクター（`Vec<Journal>`）を直接保持する設計にすると、Bookをメモリにロード・更新するたびにすべての仕訳データが芋づる式にメモリに読み込まれ、クライアントアプリのメモリ消費とパフォーマンスが著しく悪化します。

## 意思決定
`/app` のドメイン層において、**Type Stateパターンによる権限制御**と、**集約の完全分離（BookとJournalの分離）**を採用します。

```
                       [ Cabinet<State> ]  ── 最上位ルート (Type State)
                         /            \
  Cabinet<Managed> (原本)              Cabinet<Reference> (参照)
  └─ 帳簿・仕訳の編集/削除が可能          └─ リンクの追加/解除のみ可能
  
  
                     [ Book 集約 ]  ────────── [ Journal 集約 ]  (完全な別集約)
                       * ID                    * ID
                       * Name                  * BookID (弱参照)
                       * Settings              * JournalEntry (明細)
                                               * Status (未分類等)
```

### 1. Cabinet集約における Type State パターン
キャビネットの状態をRustの型システムを用いて静的に表現し、行えないはずの操作をコンパイル段階で完全にブロックします。

* 空の構造体 `struct Managed;` と `struct Reference;` を定義し、キャビネットを `Cabinet<State>` としてジェネリクス化します。
* `Cabinet<Managed>` 型に対してのみ、`create_book` や `delete_book` といった「リソースの作成・破壊を行うメソッド」を実装（`impl`）します。
* 外部共有された参照である `Cabinet<Reference>` に対しては、「リンクの追加・解除」を行うメソッドのみを実装します。これにより、開発者が誤って参照用のキャビネットに対して変更を加えるコードを書いても、コンパイルエラーとなりバグが未然に防がれます。

### 2. Book（帳簿）と Journal（仕訳）の集約分離
メモリ保護とローカルDB（SQLite）の読み込み効率化のため、BookとJournalをそれぞれ**独立した集約ルート**として定義します。

* **Book構造体**: 自身のメタデータ（ID、帳簿名、設定情報、所属勘定の構造）のみを保持し、**内部に仕訳の配列を絶対に保持しません**。
* **Journal構造体**: 独立した集約として定義され、自身がどのBookに属しているかを示す **`BookID`** を弱参照（単なるUUIDv7フィールド）として保持します。
* 仕訳の分割（`divide`）や統合（`merge`）などの状態遷移ロジックは、`Journal` 構造体自身にメソッドとして実装し、自己の不変条件（貸借対照が一致しているかなど）を自律的に検証させます。

## 影響
* **メリット**:
  * 共有データの不正操作がコンパイル時に完全に防止され、不適切な状態遷移が起こり得ない堅牢なドメインが実現。
  * クライアントのメモリ使用量が完全にフラットに保たれ、何万件の明細があっても、必要なときに必要な仕訳のレンジ（当月分など）だけを高速にオンデマンドでDBからロードできる。
* **デメリット**:
  * ある帳簿に属するすべての仕訳にまたがる不変条件（例：帳簿全体の残高と仕訳の合計が一致しているか）の検証をドメインオブジェクト単体で行うことが難しくなり、アプリケーションサービスやDB制約（トリガー/インデックス）に一部依存する必要がある。
